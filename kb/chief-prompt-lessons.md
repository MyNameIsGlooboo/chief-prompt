# Chief prompt lessons

One dated line per rule that failed or confused the agent: the rule, what happened, and why. Never prune this file.

- 2026-11-13: Rule "Copy them exactly" (prompt step 1). In this repo `CLAUDE.md` could not be an exact copy, because the repo needs its own rules too. It imports `template/CLAUDE.md` and adds a short part. Why: the prompt has no word on a project that needs extra rules in `CLAUDE.md`.
- 2026-11-13: Rule "It asks me before `git push`, `git merge`, `gh pr merge` ... deleting files" (Approval). For each of three small changes the agent asked three times: open the PR, merge, delete the branch. The owner said it should be one step with one approval. Why: the rule lists the actions one by one and has no word on asking for them together.
- 2026-11-13: Rule "Create kb/ as CLAUDE.md describes" (prompt step 3). `kb/research/` is empty at the start, and git does not keep an empty folder. Why: the rule does not say what to do with an empty folder.
- 2026-11-13: Rule "Copy them exactly and do not rewrite them. If one of these files already exists here ... stop and ask me" (prompt step 1). In a project with files, the agent stops at once (almost every project has a `.gitignore`), and the rule gives no way on but overwrite or skip. The agent also told the owner twice to update a project by copying the new `CLAUDE.md` over the old one, which would delete the Language line and the project's own rules. Why: the template mixed rules the prompt owns with lines the project edits, in one file.
- 2026-11-13: Rule "For each open task in kb/todo.md, in order" (autopilot skill). The owner started `/chief-autopilot` with two new tasks as arguments, and they were not in `kb/todo.md`. The agent added them to `kb/todo.md` itself and then worked on them. Why: the skill has no word on tasks that come with the command.
- 2026-11-13: Rule "give the `reviewer` agent the diff and the plan" (Check, then review). The reviewer has only Read, Grep and Glob, so it cannot run `git diff`. The agent wrote the diff to a file in a temporary folder outside the project. In the second review it gave no diff, and the reviewer read the files on disk. Why: the rule does not say how the diff reaches a read-only agent.
- 2026-11-13: Rule "ask one card per question" (autopilot skill, "When I am back"). The owner answered question 2 with "leave it", and the options were "keep my pick" and "change nothing", so the answer had two meanings and the agent had to ask again. Why: the agent's report listed the picks as prose, and one option was named "change nothing".
- 2026-11-13: Rule "After each task, tick `kb/todo.md` and update `kb/status.md` before you reply" (Save as you go), together with "Always work on branches". The status file was written on the branch before the PR existed, so it said "built on branch ...". After the merge it was wrong, and the fix needed its own branch, PR and approval (PR 17, and PR 15 before it, for one line each). Why: the rules do not say what the status file should say about work that is ready and not merged yet.
- 2026-11-13: Rule "Before any code merge, give the `reviewer` agent the diff and the plan" (Check, then review). The reviewer found two problems in PR 16. The agent fixed both and asked for the merge, and the reviewer did not read the fixes. Why: the rule does not say if a fix after a review needs a second review.
- 2026-11-13: Rule "ask me once for the whole step: push and PR ..., merge, and delete" (Approval). In PR 17 the merge command ran while the GitHub checks were still running, and GitHub refused it. The agent tried again and it worked. Why: the rule says "stop only if something fails" and does not say to wait for the checks of the PR before the merge.
- 2026-11-14: Rule "ask me once for the whole step" (Approval), together with the ask rules in `.claude/settings.json`. The owner works in bypass mode and still got a question from Claude Code for each push and each merge, after the yes in the chat. The session logs of this repo held 53 push and 29 merge commands that match an ask rule. Why: ask rules ask in every permission mode, and the rule did not say to run the parts as one command. Fixed in PR 20: one joined command, one question.
- 2026-11-14: Rule "give the `reviewer` agent the diff and the plan" (Check, then review). For the rule in PR 20 the only plan was a draft in `kb/research/` with "Status: research, not approved", and the reviewer reported that as a problem. The owner had said yes to the draft and to a test, not yet to the rule. Why: the rules do not say what the reviewer gets when a change comes from a research draft and the owner's yes comes after the review.
- 2026-11-14: Rule "Use them only for long, parallel, or clean-context work" (Background agents), together with "Branches from parallel writers ... I read and merge those myself" (Approval). In a real project the chief did almost all work itself, so its session was almost always busy, the owner could not talk to it, and the work was slow. Why: the first rule tells the chief when it may use an agent, not that it should stay free for the owner, and the second rule makes every parallel branch more work for the owner.
