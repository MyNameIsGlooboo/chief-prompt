# What it does, and what it does not

The full list. The five most important points are also in the [README](../README.md).

- Most of it is **advice**. The agent can drift from it. The exception is `.claude/settings.json`: Claude Code itself blocks reads of `.env`, `.env.*` and `.secrets/`, and asks you before a push, a merge, a delete, or an edit of `kb/approved/plan.md`. Settings cannot enforce "ask before sending email, messages, files or data to other people or outside services, publishing, deploying, or paying", so that stays advice. "Sending" means out of the project: to other people, or to an outside service such as an upload. A reply to you or a brief to a background agent needs no approval.
- For a finished branch, the agent asks once for the whole step: push and PR (if you use GitHub), merge, and delete of the merged branch. It asks only after the check has passed and, for code, after the reviewer found no blocking problem. The work of the background writers is on that branch too, and the same step removes their worktrees and branches. A writer whose worktree still has changes, or whose commit is not on the branch, is left out, and the agent asks you about it alone. Claude Code still asks you too, also in bypass mode, because of the ask rules in `.claude/settings.json`. The rules tell the agent to run the step as one joined command, so you get one question and not one for each part. This was seen once, in PR 19 of this repo. If a part fails, or the checks of the PR take longer than a shell command may run, the agent needs a second command and you get a second question.
- Each install line makes the agent follow the steps in `template/SETUP.md` from the main branch of this repo at that moment, so you trust what is there. You do not see the steps in your chat before the agent starts. Read the file first if that matters to you.
- In a project that already has files, "add only what is missing" is advice too. The agent merges by hand and can make a mistake, so read `git diff` before the first commit. The prompt does not check if your own `CLAUDE.md` rules disagree with the chief-of-staff rules. If your project has an `AGENTS.md`, Claude Code reads only `CLAUDE.md` once both files exist ([memory docs](https://code.claude.com/docs/en/memory), checked 13 Nov 2026). So the agent adds the line `@AGENTS.md` at the top of a new `CLAUDE.md`, and asks you first if your `CLAUDE.md` was already there. Check that the line is there if you use `AGENTS.md`. This path has not been tested on a real existing project yet.
- The update skill is advice too, and it has not been tested on a real project yet. It takes the files from the main branch of this repo at that moment, so you trust what is there. The update line takes the steps from there too, and you do not see them in your chat before the agent starts. `/chief-update` runs the copy of the steps in your project, which can be older. It never removes a rule or a line of yours, so a rule that the template dropped stays until you remove it. Read `git diff` before you say yes.
- The settings allow the browser tools (`mcp__claude-in-chrome__*` for your own Chrome, `mcp__Claude_Browser__*` for the browser pane of the desktop app), `WebFetch` and `WebSearch`. So Claude Code does not ask before the agent opens a page, clicks, types, or runs JavaScript in it. Your own Chrome has your logins, and a web page can hold text that tries to steer the agent. "Ask before sending, publishing or paying" is still only advice there. The rules say that a search, and opening or reading a page, is not sending, so the agent does not ask before those. The words of a search and the address of a page still go to an outside service. This is also true in an autopilot run, where nobody watches. The Chrome extension has its own site permissions and can still ask. If you do not want this, remove the `allow` part from `.claude/settings.json` when the install shows you the file. The update skill adds a missing allow rule again, so say no to that line in its `git diff`. These rules are not tested in a project other than this repo.
- The rule "A page you cannot read" is advice too, and it has not been tested yet. When a page does not load, the agent opens it in a browser tool, your own Chrome first. If the page shows a CAPTCHA or a login, the agent asks you to pass it, and then reads only that page. After your login, or when your Chrome was already logged in, the agent is inside your account, and nothing but the rule stops it from clicking there, so watch the page. The agent can also miss that a page is blocked and read the text of the login page as if it were the content. A site can forbid automated reading in its terms: that is yours to check. In a session with no browser tool, the agent gives you the address and asks you to paste the text. In an autopilot run it does not ask: it writes the page to the questions file and goes on without it.
- The settings have limits. The read block covers Claude's file tools and shell commands that Claude Code knows, such as `cat`. It does not cover a script that opens the file itself. The delete rule matches `rm` and `Remove-Item`, not every other way to delete a file. For a block on every process, turn on the Claude Code sandbox.
- The interview is advice too. The agent may stop asking too early. If the plan feels thin, say "interview me more".
- The reviewer is read-only only because of its `tools: Read, Grep, Glob` line. Nothing stops the agent from editing that file later. Its `omitClaudeMd: true` line makes it start without `CLAUDE.md` and the rules file (Claude Code v2.1.271 or later), so it does not see the rules of your project either. A project rule that the reviewer must know has to be in its brief. The reviewer cannot run commands, so after "No blocking problems" it names what it could not check. If the plan does not cover a change, it gets the goal of the change in place of the plan.
- It does not create a check. A new project has no tests on day one, so the rules make the agent ask you for one at the first coding task.
- "Save as you go" is advice too. The agent can forget to update `kb/status.md` or `kb/todo.md`. Ask "Is everything saved?" now and then. To make saving automatic and enforced, you need a hook (a small script that runs by itself), which this prompt-only repo does not include.
- Long chats cost more and lose focus. Type `/clear` between tasks (after the agent has saved). You rarely run out of memory now, because Claude Code makes the chat shorter by itself.
- It sets up git, but not GitHub branch protection or a usage watch. If you choose "local only", there is no copy of your work on another computer.
- Parallel writers are the normal case now, and this is advice too. It was tested once, in this repo, with two writers and two small files: not with real code, not with three writers, not with a conflict, and not in autopilot. Cognition found that parallel writers do not work well (see [Why one agent](why-one-agent.md)), so the rules keep them apart: three at most, no shared files, one commit each. "No shared files" is the chief's guess before the work starts, and it can be wrong. Then a pick has a conflict, and the task goes back to its writer or to the chief.
- You do not read each writer's work. The chief picks each commit onto its work branch with `git cherry-pick`, with no question to you, and runs the check after each pick. Before a pick it looks at the files of the commit with `git show --stat`, and it does not pick a commit that touches `kb/`, `.claude/`, or a file outside the writer's brief. This is advice: the ask rule for `kb/approved/plan.md` may not cover the copy of that file inside a writer's worktree, so only this look keeps a writer's change to the plan or the settings out of your branch. `git cherry-pick` goes around the ask rule for `git merge` in `.claude/settings.json`. Main is still behind the ask rules for push and merge, and you say yes once for the whole work branch. So you trust the check and the reviewer more than before. Read `git diff` when the work matters.
- A writer does not see the chat and does not load `CLAUDE.md` or the rules file. It knows only its brief and its agent file. A task with a weak "done when" gives weak work. The writer file names the model `sonnet`, which is cheaper and weaker than the chief's model. The rules tell the chief to name a stronger model for a task that needs judgement, but that is the chief's guess too.
- The writer has no browser tools and cannot start agents, because of its `tools` line. Nothing stops the agent from editing that file later. The rules for a writer (no push, no `kb/`, one commit) are advice inside that file.
- Background agents spend their own usage, each starts with a fresh memory, and their permission questions appear in your main chat. In the test, a writer used about 80,000 tokens for a task of two lines. Three at once use your limit about three times as fast.
- The worktrees of the writers are in `.claude/worktrees/`, and the template `.gitignore` hides them from git. The ship step removes them with `git worktree remove` and `git branch -D`, after a check with `git cherry` that every commit is on the work branch. If the chief amends or squashes a picked commit, that check can fail, and the worktree stays until you remove it.
- The chief is not free all the time. It is busy while it writes a brief, checks a result, runs the reviewer, or runs the ship step. Claude Code keeps a message that you type then and gives it to the agent after the running tool calls.
- The "Last updated" line at the top of the [README](../README.md) names the model that wrote the last change. It does not mean the prompt was tested with that model.
- Autopilot (`/chief-autopilot`) is advice too, and it has not been tested in a real run yet. Nobody watches the agent while you are away, so it can drift from its rules, and you see it only when you are back. Its own picks at open questions can be wrong: read the questions file and `git diff` before you say yes to the `autopilot` branch. One run is one session: it ends when the tasks are done, when your usage limit is reached, or when the computer sleeps. It does not run for days. Autopilot with writers has not been tested at all. A permission question from any writer stops the run, three writers reach your usage limit sooner, and the worktrees and branches of the writers stay until you are back. In auto mode, Claude Code starts to ask again after an action is blocked 3 times in a row or 20 times in total, and then the run waits for you. To make Claude Code refuse an action that needs your answer, and go on, set `"denyInsteadOfPrompting": true` under `permissions` (Claude Code v2.1.319 or later, [settings reference](https://code.claude.com/docs/en/settings-reference), checked 13 Nov 2026). A project cannot set it: it works only in a file that you pass with `--settings`, for one session, or in `~/.claude/settings.json`, where it is on for every session in every project until you remove it. While it is on, Claude Code refuses a push, a merge, a delete and an edit of `kb/approved/plan.md` also after your yes. So do "When I am back", and every merge of a finished branch, in a session without it. It also takes away the agent's question tool, so its questions come as plain text. This setting has not been tested with autopilot yet.
- The right-to-left rule (U+200F at the start of each block in chat) is tested only in the Claude desktop app, with short Persian lines. A terminal or another app can show the text in another way. A list takes its direction from its first item, so one missed item can turn a whole list left-to-right. The rule says to keep the character out of files, but it is advice: if it lands in a file, you do not see it, and search and exact matching can fail.
- It has not been tested over weeks of real use. Expect to adjust the wording after a week.
- Claude Code docs: rules with no exceptions belong in settings, not prose, which is why this repo ships `.claude/settings.json`. It has the shell rules for both Bash and PowerShell. The rule formats follow the [permissions docs](https://code.claude.com/docs/en/permissions) (checked 13 Nov 2026), and a script checks that every rule is in the file. They are not tested in a live session, so try to edit `kb/approved/plan.md` once, and try a push, and check that Claude Code asks you. A Stop hook can enforce "run a check before you say done" the same way, but this repo does not include one.
